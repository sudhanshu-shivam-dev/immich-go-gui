# Immich-Go GUI — Synthesized Code Review

## 1. Overall Health Assessment

The codebase has a genuinely strong center and a weak perimeter. The Qt-free `core/` layer — flag allowlists per tab, the `CommandPlan` seam, env-only secret delivery, masking, the declarative `ADVANCED_FLAGS` registry, and golden argv tests pinned to real captured CLI help — is disciplined work that many GUIs of this kind never achieve. But correctness degrades sharply at every boundary the core does not control: the macOS launch path cannot deliver credentials at all, the Windows `.bat` path mangles `%` and non-ASCII, the GUI wiring contains two entirely dead features (manual binary path, the folder/Picasa album fields), the profile system has two data-loss paths, and every network/subprocess call except the binary download blocks the Qt main thread. A recurring failure mode is *silent* wrong behavior — options dropped, configs overwritten with defaults, state bleeding between profiles — which is worse than crashing in a tool that launches destructive-capable CLI commands. The test suite is excellent on command construction but non-hermetic (it writes the developer's real config, keyring, and lock files) and nearly blind on runtime flows. Overall: a solid B core wrapped in C- platform glue.

## 2. Top 10 Issues (deduplicated, ranked by real-world impact)

1. **[critical] macOS runs can never authenticate — env vars don't reach Terminal.app** — `core/terminal_launcher.py:176` (also surfaced by UI, security, and tests reviews; the `_quote_sh_env_val` helper at line 49 exists for exactly this and is never called). Every server-backed run on macOS fails. *Fix: write `export IMMICH_GO_*=…` lines (via `_quote_sh_env_val`) into the 0700 `run.sh`; add a darwin launch test asserting the script contents.*
2. **[high] Cross-profile state bleed: new/loaded profiles inherit the previous profile's form data** — `app.py:2253` (`apply_form_state` never resets widgets absent from saved state; new profiles have `form_state == {}`). Saving profile B then permanently persists profile A's paths and flags. *Fix: reset all inputs and adv_rows to defaults before applying loaded state.*
3. **[high] Rename Active Profile desyncs save/load targets and keyring identity — edits after a rename are silently lost** — `app.py:2170` (+ partial-failure inconsistency in `core/profile_manager.py:296`). Next save writes a zombie `profiles/<old>/` dir and the cleared old keyring user; restart reads the new one. *Fix: call `load_configuration()` (or at minimum update `app_config.profile_name`) after rename; do the fallible secret copy before the directory rename.*
4. **[high] Manual Binary Path feature is completely dead** — `app.py:1076` (0-arg `QTimer.timeout` connected to a 1-arg slot; every fire raises `TypeError`, handler never runs). *Fix: connect a lambda that reads `manual_binary_edit.text()`.* Same wiring-class bug: `app.py:691` — QPlainTextEdit `textChanged` (0-arg) → 1-arg lambda makes every keystroke in `--ban-file` rows raise and stalls status updates.
5. **[high] Album options silently discarded on Upload From Folder and Upload Picasa** — `core/command_builder.py:535` (picasa branch never emits `--folder-as-album`/`--into-album`) and `app.py:1222` (upload-folder `into-album` widget never read into tab state); the advanced-flag key collision at `core/advanced_flags.py:744,766` makes the widgets dead in both modes. Photos upload without album assignment, no warning. *Fix: mirror the upload-folder emission in the picasa branch, read `into-album` in `_raw_tab_state`, rename the colliding advanced keys.*
6. **[high] Test suite is non-hermetic: mutates the developer's real config, real OS keyring, and deletes real run locks** — `tests/test_app.py:1575` (`reset_all_locks` on the real lock dir), `:1678` (`save_configuration` writes real `config.toml` + keyring), `:194/196` (session-scoped mutable `gui` fixture creates order-dependent passes, e.g. `test_plan_errors_surfaced_in_gui`). *Fix: a session-scoped autouse `conftest.py` setting `IMMICH_GO_GUI_CONFIG`/`HOME` to tmp_path and a fake keyring backend, plus a function-scoped or fully-reset gui fixture.*
7. **[medium×2, merged] Windows `.bat` generation is unsafe for real-world paths: `%` expansion and OEM-codepage mojibake** — `core/terminal_launcher.py:81` (`list2cmdline` output embedded raw; `%NAME%`/`%1`/`%%` semantics rewrite arguments) and `:93` (UTF-8 file read as cp850/cp437 — breaks `C:\Users\Müller`, CJK/Cyrillic paths, and the APPDATA lock paths). *Fix: escape `%`→`%%` in every string written to the bat, and emit `chcp 65001 >nul` first.*
8. **[medium, systemic] Blocking network/subprocess work on the GUI thread** — `app.py:2660` (Test Connection, 6–12 s), `:2796` (Run-button preflight, up to two 3 s probes + binary `version` subprocess), `:2974` (Check for Updates, up to ~45 s), `:1995` (compat dialog, 6 sequential `--help` subprocesses), `:3103` (`worker.wait()` after Cancel can block up to 60 s; success-after-cancel installs anyway). *Fix: reuse the existing `InstallWorker` QThread pattern for all of these; never `wait()` on the GUI thread.*
9. **[medium] Corrupt config/profile files are silently replaced with defaults, then permanently overwritten on next save** — `core/config_manager.py:199` (`load_config` swallows TOML errors) and `core/profile_manager.py:97` (corrupt `profiles.toml` rewritten containing only "default"). *Fix: distinguish absent vs unreadable, back up the corrupt file, and warn before allowing an overwrite.*
10. **[medium] macOS release artifact is arm64 but named x86_64** — `.github/workflows/release.yml:92-98` (built on Apple Silicon `macos-latest`, labeled `-macOS-x86_64.dmg`; `|| true` swallows DMG packaging failures). Intel Mac users download a binary that cannot run. *Fix: pin `macos-15-intel` or build both arches and name them truthfully; drop the `|| true`.*

Near-misses worth flagging: the glob-metacharacter path swap (`core/command_builder.py:133` — a folder named `Photos [2020]` silently resolves to a *sibling* directory; fix with `glob.escape` on browsed paths), the contradictory duplicate `--pause-immich-jobs` that re-enables the 403 the plan warns about (`core/command_builder.py:451` / `core/advanced_flags.py:1455`), and the silent `http://` default that sends the API key in cleartext for scheme-less URLs (`core/network.py:18`, duplicated in `command_builder.py:113` — default to https or warn on non-loopback http).

## 4. Readiness for a Multi-Machine Upload Orchestrator

Frankly: the data layer is closer to ready than it looks, and the execution layer is nowhere near. On the positive side, `CommandPlan` is already a pure, serializable `{argv, env, binary_path, tab_key}` contract with secrets in env rather than argv, `BinaryManager` already accepts `os_name`/`arch` as constructor parameters (an unused seam that anticipates target-side installs), and the per-run lock files carry per-job identity that the persistence layer supports for multiple concurrent runs. But everything above and around that contract assumes exactly one local machine and one job: plan building does local glob expansion and `os.path.abspath` on source paths at build time (which would mangle remote paths — plan construction must be split into control-side flag emission and target-side path resolution), liveness is inferred from local PIDs, `os.kill`, and heartbeat file mtimes, the GUI tracks only `active_locks[0]` and globally gates the Run buttons, and the sole execution strategy is "write a script and spawn a desktop terminal emulator" — fire-and-forget with no stdout capture, no exit-code propagation, and no way to cancel. Headless operation is structurally impossible today. Growing into an orchestrator requires one missing abstraction introduced three times over: a Runner/Executor interface (attached-subprocess | external-terminal | remote-agent) consuming `CommandPlan`, a jobs *collection* model replacing the single lock path, and an async service layer for the network calls currently frozen onto the GUI thread. None of that is prohibitive — the clean core/UI split means the surgery is confined to `terminal_launcher`, `process_tracker`, and the orchestration slices of `app.py` — but until the god object is decomposed and widgets stop being the only source of truth, every one of those changes lands in a 3471-line file where two entire features are already silently dead. Fix the platform-boundary bugs and test hermeticity first; then extract the Runner seam before writing any multi-machine code.

## Appendix: Full Verified Finding List

Every finding below was independently re-checked by an adversarial verifier that tried to refute it against the code; refuted findings are excluded. Severity reflects post-verification adjustment.

### core-correctness (18 findings)

> The pure command-construction core is genuinely solid — per-tab flag allowlists, env-only secret passing, masking, and the CommandPlan pipeline are coherent and well-tested — but correctness collapses at the platform boundary: the macOS launch path can never deliver credentials to immich-go (the env-export helper exists but is never called), the Windows .bat path mis-handles '%' and non-ASCII bytes, and literal paths containing glob metacharacters can silently swap the upload source to a different directory. Beyond the launchers, there is a cluster of silent-drop/silent-reset error paths (Picasa album options discarded, corrupt config/profile files quietly replaced with defaults, contradictory duplicate --pause-immich-jobs emission) where the app does the wrong thing without telling the user. Findings were verified by reading every core/ file and reproducing the glob, date-range, migration, int-crash, and help-parse bugs with executable tests.

- **[critical] macOS: secrets/env never reach immich-go — Terminal.app does not inherit the launch environment** — `core/terminal_launcher.py:176`
  On macOS the command is launched via `osascript ... tell application "Terminal" to do script (item 1 of argv)` with `env=posix_env` (lines 176-188). Terminal.app is launched/controlled via Apple Events, so the shell it spawns inherits Terminal.app's (launchd's) environment, NOT osascript's. All secrets and connection settings are passed exclusively through env vars (IMMICH_GO_UPLOAD_API_KEY etc., built in core/command_builder.py build_environment; the API key is never placed in argv). The generated run.sh (lines 130-165) contains no export statements — the helper `_quote_sh_env_val` (line 49) that exists precisely for embedding env exports into the script is defined but never called anywhere in the repo. Concrete failure: any macOS user runs any upload/stack/archive-immich command → immich-go starts in Terminal without the API key/server env vars → immediately fails with a missing-credentials error. Every server-backed run on macOS is broken. Fix: write `export KEY=<_quote_sh_env_val(val)>` lines for the IMMICH_GO_* vars into run.sh (chmod 0700 already applied), or pass secrets another way.
- **[high] upload-picasa: main-tab 'Album Organization' and 'Put all into Album' values are silently discarded** — `core/command_builder.py:535`
  The upload-picasa branch (lines 535-545) emits only manage-burst/manage-raw-jpeg/manage-heic-jpeg and path — unlike upload-folder (lines 473-475) it never emits --folder-as-album or --into-album, even though both are in TAB_ALLOWED_FLAGS['upload-picasa'] (core/cli_schema.py:205-217) and the GUI collects tab_state['folder-album'] and tab_state['into-album'] from always-visible widgets (app.py:1500-1508, 2546-2554). Worse, ADVANCED_FLAGS['upload-picasa'] reuses the keys 'folder-album'/'into-album' (core/advanced_flags.py:744,766), so in basic mode _collect_tab_state pops them and in advanced mode the builder ignores them — the visible combo box and text field are dead controls in every mode. Concrete failure: user selects 'Album Organization: FOLDER' or types an album name on the Picasa upload tab, previews and runs; the command contains neither flag and all photos are uploaded without album assignment, silently. Fix: mirror the upload-folder emission in the upload-picasa branch (and rename the advanced keys to avoid the state collision).
- **[medium] Literal paths containing [ ] * ? are treated as glob patterns and can silently resolve to the wrong directory** — `core/command_builder.py:133`
  collect_paths() runs glob.glob() on every input line without glob.escape (line 133), and validation.expand_source_paths() does the same when has_glob_pattern() sees any of * ? [ ] (core/validation.py:188-193). File-browse dialogs return literal paths, so a real directory named e.g. 'Photos [2020]' is interpreted as a character class. Reproduced: with dirs 'Photos [2020]' and 'Photos 2' present, collect_paths('/tmp/x/Photos [2020]') returned ['/tmp/x/Photos 2'] — the upload source is silently swapped to a sibling directory, and expand_source_paths produced the same wrong path with NO warning. If no sibling matches, validation emits a bogus 'Glob pattern matched no files' warning for a folder that exists. Brackets in folder names are common (especially on Windows where * ? are illegal but [ ] are fine). Fix: only glob lines the user marked as patterns, or glob.escape() paths coming from the browse dialog; at minimum verify os.path.exists on the literal path before treating it as a glob.
- **[medium] Windows: '%' in paths/values is expanded by cmd.exe because list2cmdline output is embedded raw in the generated .bat** — `core/terminal_launcher.py:81`
  The Windows branch builds `cmd_str = subprocess.list2cmdline(command)` (line 69) and writes it verbatim into a .bat file executed via `cmd /k` (lines 72-93). list2cmdline quotes for CreateProcess argument parsing, not for batch: inside a .bat, `%NAME%` is expanded even within double quotes, `%1`..`%9` are parameter substitutions, and `%%` is the escape for a literal percent. Concrete failure: source folder `C:\Users\bob\Photos %backup%` or an album value `--into-album=100% vacation` → cmd rewrites the argument (env-var expansion / parameter substitution) → immich-go receives a mangled path/album and uploads from the wrong location or errors. The lock/heartbeat paths interpolated at lines 75-76 have the same exposure for '%' in the profile path. Fix: escape '%' as '%%' in every string written into the .bat (command string, LOCK_FILE, HB_FILE).
- **[medium] Windows .bat written as UTF-8 but cmd.exe decodes it in the OEM codepage — non-ASCII paths break** — `core/terminal_launcher.py:93`
  bat_path.write_text(bat_content, encoding='utf-8') (line 93) but cmd.exe reads batch files using the console OEM codepage (e.g. cp850/cp437), not UTF-8, and there is no `chcp 65001` in the script. Any non-ASCII character — a user profile like C:\Users\Müller (which appears in LOCK_FILE/HB_FILE since locks live under APPDATA), a source folder with accented/CJK/Cyrillic characters, or an album name — is mis-decoded into mojibake, so the command targets a nonexistent path (run fails) or lock/heartbeat sidecar handling silently breaks. Fix: emit `chcp 65001 >nul` as the first bat line and keep UTF-8, or write the file in the active OEM codepage.
- **[medium] Advanced 'pause-jobs' flag contradicts the builder's admin-key auto-disable, re-enabling the 403 it warns about** — `core/command_builder.py:451`
  With no admin API key configured, build_plan_from_state emits --pause-immich-jobs=false and warns 'Job pausing disabled: no Admin API Key is configured' (lines 445-456). If the user also enables the advanced 'pause-jobs' row (default true; ADVANCED_FLAGS defs e.g. core/advanced_flags.py:136-142), apply_advanced_flags_to_plan appends a bare --pause-immich-jobs afterwards (advanced_flag_args bool branch, lines 1455-1457; appended without any dedup/conflict check at lines 1537-1541). Final argv contains both '--pause-immich-jobs=false' and '--pause-immich-jobs'; pflag last-wins semantics re-enable pausing without an admin key → the job-pause API call returns 403 and the run aborts — exactly the failure the plan's own warning claims to have prevented, making the preview actively misleading. The same append-without-dedup path allows duplicate --on-errors from config vs. advanced state. Fix: have apply_advanced_flags_to_plan drop or override earlier emissions of the same flag, and respect the has_admin_key guard for pause-immich-jobs.
- **[medium] Relative binary path breaks because launcher scripts cd away before executing** — `core/terminal_launcher.py:148`
  The POSIX run.sh does `cd "$SAFE_DIR"` ($HOME, lines 146-148) and the Windows .bat does `cd /d "%~dp0"` (the locks dir, line 74) before running the command line. build_plan_from_state defaults binary_path to the relative './immich-go' (core/command_builder.py:368) and app.py falls back to the same literal (app.py:3184, 2741); os.path.exists('./immich-go') passes when the GUI's cwd contains the binary. Concrete failure: a user who keeps immich-go next to the app instead of using the managed download launches a run → the pre-launch existence check passes, but the terminal script cds to $HOME (or the locks dir) and './immich-go' resolves there → 'No such file or directory', run fails after the lock was created. Source paths and write-to are absolutized by the builder; the binary path is the one token that can stay relative. Fix: os.path.abspath the binary path when building the plan or before writing the launcher script.
- **[medium] load_config silently swallows TOML parse errors; a subsequent save permanently overwrites the user's config with defaults** — `core/config_manager.py:199`
  load_config catches every exception from read/parse and returns a default AppConfig (lines 196-200) with no signal to the caller. If config.toml has a syntax error (hand edit, torn write), the app starts with defaults — server URL, advanced settings, and the whole form_state appear blank — and the next 'Save Configuration' (app.py:3401) rewrites the file from that default object, irreversibly destroying the user's recoverable settings without any warning. profile_manager._load_profiles_index (core/profile_manager.py:97-101) plus ensure_default_profile (lines 155-173) has the same pattern for profiles.toml: a corrupt index is silently rewritten containing only 'default', unregistering all other profiles. Fix: distinguish 'file absent' from 'file unreadable', back up the corrupt file (config.toml.bak) and surface a warning before allowing an overwrite.
- **[low] Lock files are written non-atomically while other processes delete any lock they fail to parse — torn read kills an active run's lock** — `core/process_tracker.py:75`
  create_lock (line 61) and update_lock (line 75) use Path.write_text, which truncates and rewrites in place — no tmp+os.replace. Meanwhile is_lock_active treats any unparseable lock as inactive (read_lock swallows json errors and returns None, lines 100-115/145-150) and scan_locks/cleanup_stale_locks immediately release_lock() such files (lines 211-217, 229-232). The app explicitly supports concurrent GUI instances via this lock system: instance B's periodic scan can read instance A's lock mid-rewrite (e.g. while update_lock records terminal_pid), get a JSON parse failure, and delete the active lock plus its .pid/.heartbeat sidecars — after which both instances believe nothing is running and double-run protection is gone (the Windows heartbeat loop also self-terminates when the lock file vanishes). Fix: write locks via tmp-file + os.replace, and only delete locks that parse correctly AND are provably stale.
- **[low] Pre-flight source-server check ignores the from-skip-verify-ssl setting (reads a key that never exists)** — `core/network.py:144`
  check_preflight_server_connection reads tab_state.get('from-skip-ssl') (line 144), but the GUI's tab_state for upload-immich only contains from-server/from-api-key/from-date-range/from-albums (app.py:2556-2562); the skip-SSL toggle lives in advanced_state under key 'from-skip-ssl' (core/advanced_flags.py:479-485) which is never passed to this function. Concrete failure: a user migrating from a self-signed-cert source Immich server with the from-skip-verify-ssl advanced flag enabled gets a 'Server Unreachable / SSL certificate verification failed' pre-flight warning on every run even though the actual command (which honors the flag) would succeed. Fix: pass advanced_state into the preflight and read the flag from it.
- **[low] _atomic_write_text: fixed .tmp name races between concurrent writers and no fsync before rename** — `core/config_manager.py:173`
  Every writer of a given path uses the same tmp file (path.suffix + '.tmp', lines 172-181). Two processes saving the same profile config/secrets or profiles.toml concurrently (multiple GUI instances are a supported scenario) can interleave: A finishes writing tmp, B reopens/truncates tmp, A os.replace()s B's half-written tmp into place → final file is torn despite the 'atomic' rename, and B's replace then raises FileNotFoundError. Additionally there is no f.flush()+os.fsync() before os.replace, so a power loss shortly after saving can leave a zero-length/partial config.toml or secrets.toml (rename metadata can be committed before data blocks). Fix: use tempfile.NamedTemporaryFile(dir=path.parent, delete=False) for a unique name and fsync before replace.
- **[low] int/duration advanced flags: not validated, and non-numeric value crashes command building with raw ValueError** — `core/advanced_flags.py:1470`
  advanced_flag_args does int(value) for kinds 'int' and 'duration_minutes' (lines 1469-1473) and validate_advanced_state has no branch for these kinds (lines 1561-1571), so validation passes and building raises. Reproduced: validate_advanced_state('upload-immich', {'from-minimal-rating': {'enabled': True, 'value': ''}}) → no errors, then advanced_flag_args raises ValueError: invalid literal for int() with base 10: ''. The exception propagates out of build_plan_from_state instead of landing in plan.errors. The GUI's QSpinBox path always yields ints, so the trigger is a corrupted persisted form_state or any non-GUI caller of the core API (scripts/tests); show_confirm_dialog's build_plan call (app.py:2785) has no try/except around it. Fix: validate int-kinds in validate_advanced_state and convert defensively in advanced_flag_args, routing failures into plan.errors.
- **[low] Binary metadata schema-1 migration never executes for legacy files lacking a schema_version key** — `core/binary_manager.py:146`
  load_binary_metadata seeds the dict with schema_version=2 (lines 129-134) and then meta.update(loaded); a genuine legacy v1 metadata.json that simply has no 'schema_version' key keeps the preset 2, so the `< 2` migration (lines 146-156) that backfills gui_tested/support_status/sha256/release_url never runs. Reproduced: loading {'selected_version': '0.24.0', 'versions': {'0.24.0': {'path': '/x'}}} returns record keys ['path'] with schema_version stamped 2 — the file is marked migrated without being migrated. Consequence is mild (downstream code tolerates missing keys) but any code trusting support_status/gui_tested in the record will KeyError or misclassify. Fix: read loaded.get('schema_version', 1) before merging defaults.
- **[low] clean_version/parse_version_output fallbacks produce garbage version strings** — `core/binary_manager.py:74`
  clean_version strips a leading 'v'/'V' from any string: reproduced clean_version('Version 0.32.0') → 'ersion'. parse_version_output falls back to clean_version(lines[0]) when no semver is found: reproduced parse_version_output('immich-go unknown build') → 'immich-go'. check_binary then displays 'Binary: immich-go' / 'Binary: ersion' with UNKNOWN support instead of an honest 'could not parse version' state. Trigger: any immich-go build whose `version` output lacks an x.y.z token (dev builds, error text on stderr). Fix: only strip 'v' when followed by a digit, and return '' from parse_version_output when the regex finds nothing.
- **[low] parse_help_flags drops the second long flag when two appear on one help line** — `core/cli_help.py:9`
  _FLAG_PATTERN's trailing (?:[=[\s]|$) consumes the whitespace that the next match's (?:^|\s) prefix needs; reproduced: parse_help_flags('--alpha --beta') → {'alpha'} only. Cobra normally prints one long flag per line so current fixtures parse fully, but a future immich-go help layout listing aliases like '--x, --y' on one line would make cli_contract.check_fixtures/check_binary_help falsely report GUI flags as missing (supported=False) or miss unknown flags. Fix: use lookarounds ((?<!\S)--([a-zA-Z0-9-]+)(?=[=[\s]|$)) so matches do not consume the separator.

### performance (10 findings)

> The pure-logic core (command building, validation, schema lookups with frozensets, lru_cached stylesheets and icon cache) is cheap and well-factored, and the binary download is correctly threaded; scripts/ are one-shot dev tools with no meaningful inefficiency. The two systemic problems are (1) synchronous network/subprocess calls on the Qt main thread — Test Connection, the Run-button preflight, Check for Updates, and the compatibility dialog all freeze the window for seconds (tens of seconds worst case), and (2) the undebounced update_status pipeline that runs recursive filesystem globs twice per keystroke and once per second during runs, which is the only true hot path in the app. Startup is bounded but does everything eagerly (subprocess version check, two keyring/D-Bus reads, ~1000 widgets including 196 hidden advanced-flag rows, and a duplicated full-tree stylesheet application), likely costing 1-3s of avoidable time-to-first-paint. ### security (5 findings)

> The secret-handling architecture is fundamentally sound: API keys flow to immich-go through the process environment rather than argv (build_environment/ENV_KEY_MAP), the default store is the OS keyring with a documented plaintext fallback, command previews and the env panel mask secret flags and *_API_KEY vars, TLS verification is on by default, no secrets are logged, and archive extraction writes only the known basename so Zip-Slip is avoided. The most material gap is the silent http:// default, which can transmit the Immich API key in cleartext when a user omits the scheme. Two other real issues are the absence of any checksum/signature verification on downloaded binaries (the stored SHA256 is only cosmetic) and a write-then-chmod race that briefly exposes the plaintext secrets file. The remaining items are low-severity defense-in-depth hardening.

- **[medium] Silent HTTP downgrade transmits the Immich API key in cleartext** — `core/network.py:18`
  normalize_server_url() (core/network.py:18-25, duplicated at core/command_builder.py:113-122) prepends 'http://' whenever the user-entered server URL lacks a scheme: `if not (url.startswith('http://') or url.startswith('https://')): url = 'http://' + url`. Concrete failure: a user types a bare host `immich.example.com`. test_immich_connection() (core/network.py:45-57) then sends `headers = {'x-api-key': api_key}` to `http://immich.example.com/api/server/about` with verify=... over an unencrypted connection, and build_plan_from_state() emits `--server=http://immich.example.com` so the live immich-go run also uses plaintext with the key in IMMICH_GO_*_API_KEY. The API key (a full-access Immich credential) is exposed to anyone on the path with no warning. This is a silent security downgrade. Fix: default the scheme to https://, or refuse/warn when http:// is used against a non-loopback host, and surface a visible warning in the connection-test and command-preview flows the way skip-ssl already does.
- **[low] Binary download has no checksum/signature verification; stored SHA256 is cosmetic** — `core/binary_manager.py:521`
  download_and_install() (core/binary_manager.py:521-599) fetches the immich-go archive over HTTPS and then only calls verify_extracted_binary() (line 498), which merely runs `immich-go version` to confirm the file is a runnable binary — not that it is authentic/untampered. No authoritative checksum is fetched or compared, even though upstream simulot/immich-go publishes a checksums.txt with each release. calculate_sha256() (line 122) is invoked solely in select_version() (lines 686-689) to record the hash of whatever was downloaded into metadata.json, giving a false impression that integrity is verified when nothing is checked against a source of truth. Failure scenario: a corrupted/tampered release asset (or any TLS interception that the environment's trust store accepts) yields a malicious binary that passes the `version` check and is then executed with the user's server URL and API key in its environment. Fix: download the release checksums.txt (or per-asset .sha256) from GitHub, compute the SHA256 of the downloaded archive, and abort the install on mismatch before extraction/selection.
- **[low] Atomic write leaves secrets.toml temp file world-readable during a race window** — `core/config_manager.py:169`
  _atomic_write_text() (core/config_manager.py:169-181) writes the temp file with `tmp.write_text(text)` FIRST and only afterwards calls `os.chmod(tmp, mode)`. When save_secrets()/save_secret_with_fallback() (lines 285-291, 320-356) persist the plaintext-file fallback with mode=0o600, the intermediate `secrets.toml.tmp` is created under the process umask (typically 0644 = world-readable) and stays that way until the chmod runs, inside a profile directory that mkdir created at the default 0755. Failure scenario: on a shared/multi-user host — exactly where the keyring-unavailable plaintext fallback is used — a local attacker polling the profile directory can read the API key from secrets.toml.tmp during the write-then-chmod window before os.replace makes the final 0600 file. Fix: create the temp file with restrictive permissions from the outset, e.g. os.open(tmp, O_WRONLY|O_CREAT|O_EXCL, 0o600) (or set umask 0o077 around the write), rather than chmod after writing.
- **[low] Profile path helpers do not re-validate names against path separators (defense-in-depth)** — `core/profile_manager.py:61`
  sanitize_profile_name() (core/profile_manager.py:61-63) only strips whitespace, and profile_dir()/profile_config_path()/profile_secrets_path() (lines 45-58) build filesystem paths as profiles_root()/safe_name with no rejection of '/', '\\', or '..'. Strict validation lives only in validate_profile_name() (lines 66-89), which is enforced by create_profile() but bypassed by every other path-resolving caller (load_config(profile_name=...), default_config_path, active-profile reads from profiles.toml, copy_from in create_profile). Failure scenario: a name containing path traversal that reaches profile_dir() from a tampered/hand-edited profiles.toml index or a future caller resolves outside profiles_root(), letting config/secret reads or shutil.rmtree in delete_profile() escape the intended directory. Fix: enforce sanitize/validation (reject separators and dot-segments) inside profile_dir() itself so path construction cannot be reached with an unsafe name.
- **[low] Dead secret-quoting helper hints at prior shell-embedding of secrets** — `core/terminal_launcher.py:49`
  _quote_sh_env_val() (core/terminal_launcher.py:49-51) escapes a value for `export` in a bash script but is never called; launch_external_terminal() correctly passes secrets only through the subprocess.Popen env= parameter (lines 106, 186, 208-212) and never writes them into run.sh/the .bat sidecar. The current design is safe (secrets stay off argv and out of the on-disk script), but the unused helper is a latent regression hazard: a future edit could reintroduce writing exported secrets into the world-adjacent run.sh (created in a shared temp dir, albeit chmod 0700). Fix: remove the dead helper, or add a comment asserting secrets must never be embedded in the generated script.

### architecture (14 findings)

> The architecture is better than the 3471-line app.py suggests: core/ is a disciplined, genuinely Qt-free layer (models, cli_schema allowlists, command_builder, process_tracker, binary_manager) with CommandPlan as a clean serializable seam, and the ADVANCED_FLAGS registry shows the team knows how to do declarative, data-driven extension. The two real structural problems are (1) ImmichGoGUI is a god object holding all UI construction, state (widgets are the only source of truth), orchestration, and update UX, with primary per-tab flags hand-coded in three parallel elif chains; and (2) the execution model is hard-wired to 'spawn a local desktop terminal emulator and infer liveness from lock/heartbeat files' — the GUI never owns the child process, so concurrent jobs (UI tracks only active_locks[0] and gates Run globally), remote/agent execution (local PIDs, local paths absolutized at plan time, host-arch binary management), and headless operation (hard failure without a terminal emulator, no attached-subprocess mode) all require introducing the same missing abstraction: a Runner/Executor interface plus a job collection model. The packaging pipeline is functional and reasonably automated (release-please -> tag -> 3-OS Nuitka matrix -> 7 artifact formats) but ships an arm64 macOS binary labeled x86_64 and duplicates build config between app.py directives and workflow flags.

  ImmichGoGUI (app.py:546-3451) mixes eleven hand-built per-tab form builders (_build_upload_folder_tab..._build_stack_tab, lines 1167-1883), theme handling (708-757), menu/profile CRUD (1940-2214), form-state persistence (2216-2295, 3255-3432), validation orchestration (2618-2638), binary-update UX including a QThread class defined inline inside a method (InstallWorker, 3074-3090), lock-file polling (3129-3158), and process launch (3177-3235).
